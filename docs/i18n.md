# Languages & Translation

Open Historia is written in English and played in **Arabic** (the default) or English. Every string the game shows falls into one of three kinds, and each kind is translated differently:

| Kind | Examples | Translated by | Cost to the player |
|---|---|---|---|
| **Interface** | buttons, tabs, labels, hints, errors, the tutorial, stock country names, the built-in scenarios' cards | the **shipped language packs** (`public/lang/<code>.json`) | nothing |
| **Content** | a scenario's and a saved game's name and description, polity names, roles and notes, the scenario's own events, a custom Stats sheet, region names, country names a pack lacks, Community posts | the player's **AI model**, once, then saved to the server's language pack | a few requests the first time a language meets that content |
| **AI writing** | events, chats, the advisor, summaries written during play | nobody: the model writes them in the player's language (`languageDirective`) | nothing extra |

The default prompts' **guidance passages** (the role, the tone, what makes a good event: the parts an author edits in the Prompts tab) ship translated too (`public/lang/prompts/<code>.json`), so the model that runs the world reads its instructions in the player's language wherever the scenario has not written its own. The prompts' technical template (placeholders, output contracts, map rules) stays English, because the game parses what it asks for.

Related pages: [Runtime services](runtime-services.md) · [Prompt-Making Guide](ai-prompts.md) · [Server](server.md) · [Web build](web-build.md)

## The languages the game ships

The picker offers exactly two, in order:

| Code | Role | Pack |
|---|---|---|
| `ar` | Arabic — the default (`DEFAULT_LANGUAGE`) and the only language with a shipped pack | `public/lang/ar.json` + `public/lang/prompts/ar.json` |
| `en` | English — the language the game is authored in (`SOURCE_LANGUAGE`) | none: the source text **is** the interface, so nothing needs translating |

`LANGUAGES` in `src/runtime/i18n.js` is that list; `SHIPPED_PACK_LANGUAGES` is `["ar"]`. `src/runtime/languagePacks.test.js` fails if the shipped list and the files in `public/lang/` disagree.

- **Arabic (packed)**, the interface is never sent to the AI. A string the pack lacks stays English and is recorded in `window.__ohI18n.missing` (a `Set`, capped at 3,000) for the next pack; `window.__ohI18n.pending` is what is queued for the AI.
- **English (authored)** needs no translator at all: `startTranslator()` sets `<html lang="en" dir="ltr">` and returns before the observer starts.
- A stored code the picker no longer offers (an old `de`, say) is normalized back to Arabic by `normalizeLanguage()` at read time, so nothing can strand a player on an interface no build can render.

## The files

| File | Holds | Made by |
|---|---|---|
| `public/lang/catalog-en.json` | every English interface string, sorted: exact strings and patterns; plus every stock country name, the preset scenarios' card text, and the built-in scenarios' polity names and aliases (`server/seed/*/world.json`) | `scripts/i18n/build-catalog.mjs` |
| `public/lang/<code>.json` | `{ "<English>": "<translation>" }` for the catalog | translation (below) |
| `public/lang/prompts/catalog-en.json` | every guidance passage of the default prompts | `scripts/i18n/build-catalog.mjs` |
| `public/lang/prompts/<code>.json` | `{ "<English passage>": "<translated passage>" }` | translation (below) |
| `server/data/lang/<code>.json` (desktop) / IndexedDB `lang:<code>` (web) | translations the AI made at runtime: the **content** a pack cannot know (scenario/game names and descriptions, custom polities and stats, region names, country names the pack lacks, Community posts) | the translator, via `PUT /api/lang/:code` |

`GET /api/lang/:code` (`server/server.js`, and `handleLang` in `src/runtime/web/settingsStore.js` for the web build) returns the saved pack **under** the shipped one: the shipped entry wins, because a saved entry for a string the pack now covers is an older AI translation. `PUT` does not save a string the shipped pack already has.

### Patterns

A string built around a value is a **pattern**: the value is a slot in double braces, named after the expression it came from.

```
"Found {{count}} regions"              → "تم العثور على {{count}} منطقة"
"{{name}} declared war on {{target}}"  → "أعلنت {{name}} الحرب على {{target}}"
```

A translation keeps every slot and may move it. Plain interface text never contains `{{`, so a key with a slot is a pattern. A choice of strings is expanded into each variant, never a suffix slot: `` `${n} game${n === 1 ? "" : "s"}` `` gives `"{{n}} game"` and `"{{n}} games"`.

## How the game applies a pack — `translator.js` + `phraseBook.js`

`startTranslator()` (called from `src/main.jsx`) sets `<html lang>` and `<html dir>` from the chosen language, then returns at once for English. Arabic goes on: it puts `.oh-rtl` on `<body>`, starts loading the prompts' passages (`loadPromptTranslations`), reads this device's cache, fetches `/api/lang/:code`, waits for the startup screen to go, then walks the DOM and watches it with a `MutationObserver`.

### Right-to-left (Arabic)

Arabic is the default and the interface is laid out for it:

- **`dir="rtl"` on `<html>`** (set by `startTranslator`, and statically in `index.html` for the first paint) mirrors the HTML UI: flex rows reverse, `text-align: start/end` flips, and every logical margin/padding/border follows the writing direction. Components use **logical** properties for that reason — `marginInlineStart`, `paddingInlineEnd`, `borderInlineStart`, `textAlign: "start"` — never the physical `marginLeft`/`textAlign: "right"` a mirrored row would leave on the wrong side.
- **The map is not mirrored.** Panel/dock anchors stay physical (`position: fixed` `left`/`right`, and the `SAFE_LEFT`/`SAFE_RIGHT` notch insets) so the HUD keeps the side it was placed on and never fights the canvas, which has no direction. Canvas-drawn map labels and the two charts keep their own `textAlign` and are never touched by the direction of the DOM.
- **`.oh-rtl` on `<body>`** turns off letter-spacing and synthesised italic for the Arabic script (see `styles.css`): the tracking the UI sets inline for Latin capitals would break the cursive joins.

**Lookup** (`createPhraseBook()` in `src/runtime/phraseBook.js`, pure and tested in `phraseBook.test.js`):

1. the exact string, then the string with its whitespace collapsed;
2. a **date**: the game writes its dates in English ("Jan 1, 2016", "1 March 218 BC", "2016-01-08", from `formatGameDateReadable` in `gameDates.js` and dayjs), and the same functions write the dates the AI reads, so they stay English at the source. `createDateLocalizer` (`src/runtime/localDates.js`) recognizes a string that is exactly one of those shapes and writes it the player's way with `Intl` ("1 يناير 2016"), always in the Gregorian calendar and with **Latin digits** — Arabic-Indic numerals (`١٢٣`) are never substituted;
3. the patterns, most literal text first: the slots capture the values, each value is itself looked up, exactly or as a date (so `"Edit {{label}}"` over "Edit Borders" reads "Grenzen bearbeiten"), and the translation is filled in;
4. a **list** joined with " / ", " · ", " • " or " | " ("Modern Day Session / Japan / 2016-01-01"), which no pattern holds because it has no words of its own: each part is looked up by itself, and the list changes only when some part is known. Dashes are not separators, since prose uses them.

Two guards keep a short pattern from rewriting prose that merely starts with its words (an English reply in a chat set to another language, say): a **weak** pattern (fewer than 8 letters of its own, like `"Our {{label}}"`) accepts at most 4 words of value, and no value that mixes words and numbers unless the book knows it ("Found 12" before `"{{value}} regions"` is the start of another sentence; "Jan 1, 2016" is a date); and a value never spans two sentences unless the pattern has 16 or more letters of its own. Two slots with nothing between them are never compiled (they cannot be told apart).

**The DOM:**

- A text node is looked up by its English. The translator remembers, per node, the English it last saw and what it wrote (`nodeRecords`), so its own writes are never mistaken for source text and React's next write (new English) is translated again.
- **Runs.** React renders `<p>Found {count} regions</p>` as three text nodes. A parent whose children are all text nodes is read as one string; when the pack knows it, the whole translation goes in the first node and the others are emptied (they keep their English, so React's next update to any of them re-composes the sentence). When the pack does not know the whole, each piece is looked up on its own.
- **Attributes:** `title`, `placeholder`, `aria-label`, `aria-description`, `alt`, observed as they change; and `document.title`.
- **Skipped:** `script, style, noscript, input, textarea, [contenteditable], [data-no-translate]` (an input's own `placeholder` and `title` are still translated).

**Precedence:** the server's pack (shipped over saved) is laid over this device's cache (`localStorage["i18n_v2_<code>"]`), so a stale local translation never hides the pack's. The cache holds only what the AI translated on this device and the server does not have yet. The pre-pack caches (`i18n_cache_*`) are removed on boot; what they held that the server lacked is sent to it first.

**Map labels** are not DOM: `translateLabel(name)` (used by `countryLabels.js` and `Nations.jsx`) looks the name up and queues it as content when unknown. Labels bake translated names into map features, so a translation that lands after a label was drawn makes those features stale and they must be rebuilt — but only then. `translateLabel` therefore records every name it is asked for, and when a batch actually translates one of them the translator emits **`"i18n:labels-updated"`** (debounced, separate from `"i18n:updated"`). The builders listen to that event alone: `"i18n:updated"` fires on every content batch too, and rebuilding the whole label atlas on each one froze the map while panels were translating. Because a batch may translate no label at all, the rebuild is additionally gated on the names themselves: `countryLabels.js` fingerprints the names a tile would draw (`countryLabelNameSignature`) and stamps them onto the payload it cached (`labelSignature`), so a forced rebuild with unchanged names returns the cache. The country labels of a scenario's own map are built in the political worker from those names, and two labels that read alike fall back to their owners' names; that comparison (`labelFoldKey` in `Nations.jsx`) keeps letters of every script, since a fold to a-z made every Chinese or Arabic name the same empty key and put every label back in English. City names on the map are not translated.

## Content

Content is whatever a scenario's author or a player made. It is gathered up front, so it is translated in a few big requests instead of one panel at a time:

- **At boot and on every switch of save** (`oh:active-game-changed`), `collectContentStrings()` queues: scenario and game cards (`/api/scenarios`, `/api/games`), country names the pack lacks, every polity's name, aliases, role, note and map labels (`world.polityOverrides`), the scenario's own events (those whose `source` is `"scenario"`; the AI's events are already in the player's language), a custom Stats sheet's section and stat labels, descriptions and units, Community posts, and last (the big set) region names.
- **As it is written:** `library.js` calls `enqueueContentStrings(payload)` when a scenario or game is created or saved; `gameState.js` calls it for `polityOverrides` on every world write and `enqueueEventStrings(events)` on every event-log write; `communityHub.jsx` calls `enqueueStrings` for fetched posts.

Anything already known is never queued. The queue is sent one request at a time, up to 240 strings or 6,000 characters a request (`planTranslationBatch`; `translatorBatching.test.js` pins the sizes), halving on a failure and backing off for a minute after three. Results are saved to the server's pack (`PUT /api/lang/:code`), so each string is paid for once, on every device. The requests show as "translation" in Settings → AI, "Used today, by task".

## The prompts

`src/runtime/promptTranslations.js` holds the loaded passages. `localizedGuidanceDefaults()` in `src/Game/AI/gameplayPrompts.js` is the default guidance tree with every passage the pack translates swapped in (memoized by `promptTranslationsVersion()`), and:

- `normalizePromptPack()` composes each prompt from its English template with the **localized defaults under the author's own passages** (`localizedPassages`). An author's passage is theirs, in whatever language they wrote it.
- `normalizePromptGuidance()` drops an edit identical to the localized default, as it drops one identical to the English default (`withoutLocalizedDefaults`), so opening and saving the Prompts tab in Arabic never pins Arabic wording into a scenario other players read.
- The Prompts tab (`PromptSectionEditor` in `libraryBar.jsx`) shows the localized defaults and re-renders when they load.
- `ensurePromptsLoaded()` in `src/Game/AI/main.jsx` keys its cache on the passages' version, so prompts composed before the passages arrived are recomposed.
- Exports and transfers (`materializePackGuidance`) use the English defaults.

The passages are keyed by their English text: a passage whose wording changes simply falls back to English until the packs are regenerated, and a branch whose prompts differ finds only the passages it shares.

## Writing interface code that translates well

The catalog is read out of the source (`scripts/i18n/extractStrings.mjs`), so the way a string is written decides whether a language can translate it:

- **Keep a sentence in one template or one run of text.** `` `${count} regions found` `` or `<p>Found {count} regions</p>` is one pattern a language can reorder. A sentence split around an element (`Found <b>{count}</b> regions`) becomes pieces ("Found", "regions") translated separately.
- **Plurals and variants as whole words:** `` {n === 1 ? "event" : "events"} `` or `` event{n === 1 ? "" : "s"} `` both expand into both variants. Never build a word from pieces a language cannot reorder.
- **Names, codes, numbers and anything the player typed** go in an element marked `data-no-translate`, so they are neither looked up nor mistaken for interface.
- Text-bearing props are read from JSX (`label`, `title`, `hint`, `description`, `placeholder` and the rest of `DISPLAY_KEYS`), from registries in the directories the extractor reads (`src/runtime`, `src/Game/GameUI`, `src/Game/Selection`, `src/Game/Map`, `src/Editor`), and from status setters (`setStatus(...)`, `STATUS_CALLS`). A camelCase key ending in `Label` (`mappedLabel`, `centerSubLabel`) counts too, and its value may be a single lowercase word ("landscape"), which elsewhere would read as an id.
- **A screen shows what it catches.** Every `.jsx` file's thrown and returned prose is read (`throw new Error("Give the group a name.")`), because its screen puts `error.message` in front of the player.
- **Name a constant for what it holds.** Every string in an `UPPER_SNAKE` constant ending in `_LABEL(S)`, `_HINT(S)`, `_INTRO`, `_NOTE(S)`, `_TEXT(S)`, `_MESSAGE(S)`, `_TITLE(S)`, `_DESCRIPTION(S)`, `_BLURB(S)`, `_CAPTION(S)`, `_TOOLTIP(S)` or `_PLACEHOLDER(S)` is read as display text (`STRUCTURED_MODE_LABELS = { auto: "Automatic (recommended)" }`). A constant so named but written for the model goes in `MODEL_CONSTANTS` in the extractor.
- `src/Game/AI/*.js` is prompts and parsers, and is not read, except the registries behind Settings → AI and the Prompts tab (`JS_REGISTRY_FILES`) and the modules whose messages the player reads (`MESSAGE_FILES`: the provider failures, the Fallback list, the context window, the request budget), whose returned and thrown prose is read. The institutions' modules are message modules too (`institutionLifecycle(Core)`, `institutionalGovernance`, `institutionalChannels`, `institutionAuthoring`, `politicalWorldCapability`, and the advisor's and Game Master's institution helpers): what they refuse with shows in the Institutions tab, and the events and channel lines they write are read in the log. A new module of player-facing messages belongs in that list.
- **Write an event or a log line as one sentence per case**, not a sentence assembled from a verb looked up in a table (`${subject} ${actionLabel} ${name}`): a language can translate `"{{subject}} Joins {{name}}"`, never `"{{subject}} {{actionLabel}} {{name}}"`. `lifecycleEventTitle` and `outcomeEventDescription` are the pattern.

## Arabic typography

Arabic is the one shipped language whose script needs its own typeface. A Latin interface can leave `font-family` unset and land on whatever the system calls sans-serif; Arabic cannot, because the system's answer differs by platform (Segoe UI on Windows, Geeza Pro on macOS, Noto Naskh Arabic on Android) and the browser picks per element, so one screen drew two Arabic faces and every platform looked different.

`src/styles.css` declares the two faces over the Arabic blocks only, and `runtime/fontStacks.js` spells the same three stacks out for the contexts that cannot read a CSS custom property:

| Custom property | Stack | Where |
|---|---|---|
| `--oh-font-ui` | `"IBM Plex Sans Arabic", "Segoe UI", system-ui, sans-serif` | the whole interface |
| `--oh-font-display` | `"Amiri", "Cinzel", "EB Garamond", serif` | the loading screen's headings, the game's wordmark |
| `--oh-font-serif` | `"Amiri", "EB Garamond", Georgia, serif` | the loading screen's shell (the one place that wants EB Garamond, not Cinzel) |
| `--oh-font-mono` | `ui-monospace, Consolas, "IBM Plex Sans Arabic", monospace` | code, addresses, the debug console |

The Arabic face leads every stack on purpose, and it is safe because each `@font-face` carries `unicode-range` over the Arabic blocks (`U+0600-06FF` and the presentation forms) and nothing else: the browser skips a family whose range excludes the character, so Latin text still resolves to Segoe UI / Georgia / Consolas character by character, and a web page with no Arabic on it never downloads the fonts. `runtime/fontStacks.js` holds the same names for `ctx.font`, a Chart.js tick and MapLibre's `text-font`; `src/runtime/fontStacks.test.js` fails if the two lists drift.

Three things follow from the script being cursive, and all three live in the `.oh-rtl` rule that `translator.js` puts on `<body>` for `ar`/`fa`/`ur`/`he`:

- **No tracking.** An Arabic word is one joined run, and the `letter-spacing` the interface uses to make Latin capitals breathe — 169 call sites, and up to `1.1em` in the atlas-style map labels — visibly breaks the joins. The reset needs `!important` because most of that spacing is set inline in JSX, which no stylesheet rule outranks otherwise.
- **No synthesised italic.** There is no true italic Arabic in the bundle, and the browser's slanted fake is worse than upright text.
- **No synthesised weight.** `font-synthesis: none`, so a missing bold face is not faked into a smeared one.

The map labels are drawn on a canvas rather than as DOM (`labels/polityTextCustomLayer.js`), so two things are separate there: the Arabic faces are inserted before the Latin ones in the label stack — before Times New Roman, which carries Arabic on Windows — and `preferredLetterSpacing`/`maxLetterSpacing` return `0` for a name containing Arabic script, because a canvas letter-spacing has the same effect on the joins as a DOM one. `waitForFontStack` loads the stack against a sample of both scripts, since a canvas bakes whatever face is loaded at raster time into the texture. The date and number formatting is unchanged: the interface keeps Latin digits, the decision `localDates.js` already made.

## Regenerating the packs

1. **Build the catalogs.** One catalog serves every branch: pass the other branches' trees and it is their union, so the same packs ship everywhere.

   ```
   git archive origin/beta src scripts/presets | tar -x -C ../tree-beta
   git archive origin/main src scripts/presets | tar -x -C ../tree-main
   node scripts/i18n/build-catalog.mjs --also ../tree-beta --also ../tree-main
   ```

2. **Translate what is new.** With an OpenAI-compatible endpoint (the key is read from the environment and never written anywhere):

   ```
   OH_LLM_BASE_URL=… OH_LLM_KEY=… OH_LLM_MODEL=… node scripts/generate-lang-packs.mjs --all
   ```

   It is incremental (only strings a pack lacks are sent), drops entries the catalog no longer has, rejects a translation that loses a placeholder, and does the prompt passages too, one per request. `--lang ar` for one language, `--dry-run` to count, `--force` to redo everything. `--all` regenerates every language in the generator's `LANGUAGES` map — Arabic only, today.

3. **Check.** `node --test src/runtime/languagePacks.test.js`: every pack on disk is listed in `SHIPPED_PACK_LANGUAGES` and back, every placeholder survived, and each pack covers at least 90% of its catalog.

To add a language: add it to `LANGUAGES` and `SHIPPED_PACK_LANGUAGES` (`src/runtime/i18n.js`) and to `LANGUAGES` in `generate-lang-packs.mjs`, add its code to `RTL_LANGUAGES` if it reads right-to-left, then run step 2 for it. A language with no pack would instead fall back to AI translation of the whole interface, which no build ships any more.
